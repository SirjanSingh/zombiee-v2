## 0. TL;DR

We are switching from **single-scalar GRPO over a K-action completion** to
**per-step PPO over the 60-step trajectory**, with a value head trained
alongside the policy. Concretely:

| Aspect | Now (GRPO, runs 1-4) | Proposed (PPO, run 5+) |
|---|---|---|
| Time-step granularity | One per completion (the model emits K=1-5 actions per call, scored as a sum) | One per env step the model controls (~30 per episode at K=1, ~10 at K=5) |
| Reward signal | One scalar per completion: `step1_weight * Σ raw_step_rewards + cum_reward + format_bonus` | The env's per-step `raw_reward` at A0's turn, with bootstrap value at end |
| Credit assignment | None inside the completion. Group-normalised across G=8 generations | GAE-λ over the trajectory, advantage per action |
| Value function | None (GRPO has no V(s)) | `AutoModelForCausalLMWithValueHead` — small linear on top of the LM's last hidden state |
| Policy gradient | Group-relative (GRPO) — leans on within-group reward std | PPO clipped objective with old-vs-new logprobs |
| KL control | β·KL to reference model on every token of the completion | Per-token KL on the action tokens only, plus optional adaptive β |
| Library | `trl.GRPOTrainer` | Hand-written loop using `trl.AutoModelForCausalLMWithValueHead` + `peft`. **NOT** `trl.PPOTrainer` — see §2.1 |

**Why this and not just "more GRPO"**: the failure mode we have is that
KL stays at 0 across all 60 steps even when reward_std is healthy. The
GRPO gradient cannot tell the model which of its K actions in the
completion was actually the good one — every action shares the same scalar
reward. PPO with a value head fixes exactly this by giving every action
its own advantage estimate.

**Why not `trl.PPOTrainer`**: TRL's `PPOTrainer` is RLHF-style — it takes
prompts, generates one completion, scores with a reward model, and runs
PPO over the *token positions inside that single completion*. It does NOT
support a multi-step environment where the same policy is queried 30
times in sequence with different observations. We need the value head
wrapper from TRL and the clipped-loss math, but the training loop is
ours.

## 1. Goal & success criteria

**Single concrete goal of run 5:** beat the v2.2 heuristic baseline on
`mean_alive_at_end` (currently ~1.6 / 5) by a statistically meaningful
margin (≥0.3 alive on average over 30 eval episodes). Stretch: push
`mean_episode_length` past 30 (heuristic dies at ~16).

**What we are NOT trying to achieve in run 5:**
- Survival % > 0 (still binary; not the right metric — see memory:
  `eval_metric_binary_threshold`).
- Multi-agent training (A0-only stays).
- Beating any external baseline.
- More than 50 outer training steps.

**Validation gates** (we abort the run rather than burn DGX time if any
fails):

1. **Grad sanity** (existing): at least one LoRA param + the value head
   linear receive a non-zero, finite gradient on the first forward/backward.
2. **Logprob round-trip** (new): tokens generated by `model.generate()`
   followed by `model.forward()` on the same `(prompt + action)` must
   yield the same logprobs to within 1e-3. If not, our PPO ratio is
   garbage. Standard PEFT/4-bit pitfall — must check before training.
3. **Value sanity** (new): on a held-out batch of 20 random
   observations, V(s) outputs should be finite and reasonably bounded
   (|V| < 50). A NaN here means the head was wired wrong.
4. **Advantage flow** (new): on the first outer step, advantage variance
   must be > 0 (else we have no learning signal).

If 1-3 fail, the run aborts before the first PPO update.

## 2. Architecture

### 2.1 Why hand-rolled, not `trl.PPOTrainer`

In TRL 0.15.2, `PPOTrainer` expects:

```python
trainer = PPOTrainer(
    args=PPOConfig(...),
    processing_class=tokenizer,
    model=value_head_model,          # AutoModelForCausalLMWithValueHead
    ref_model=ref_model,
    reward_model=reward_model,       # AutoModelForSequenceClassification — not a callable!
    train_dataset=prompt_dataset,
    ...
)
trainer.train()
```

It does the rollouts itself (one completion per prompt), scores them
through `reward_model.forward()`, and runs PPO. There is no hook to say
"score this completion in an env, then ask for another completion on the
next env observation". We would have to monkey-patch the rollout method,
at which point we have written a custom trainer with extra steps. We
write the loop directly.

What we DO use from TRL:
- `AutoModelForCausalLMWithValueHead` — the model+value-head wrapper.
  Loads any HF causal LM, adds a scalar head over the last hidden state
  (~1 MB of params), and exposes `model(...).value` alongside logits.
  Plays nicely with PEFT/LoRA — the LoRA is on the base, the value head
  is fully trained.
- Clipped-objective formula (we'll copy the few lines from `ppo_trainer.py`
  so we don't drift).

### 2.2 Model wrapping order

```python
base = AutoModelForCausalLM.from_pretrained(..., quantization_config=bnb_4bit)
base = prepare_model_for_kbit_training(base, use_gradient_checkpointing=False)
base = get_peft_model(base, LoraConfig(r=32, alpha=64, target=q,k,v,o))
model = AutoModelForCausalLMWithValueHead.from_pretrained(base)
# At this point:
#   - 4-bit frozen base weights
#   - LoRA adapters trainable (r=32)
#   - value head trainable (Linear(hidden_size, 1) + small dropout)
# Reference model: same load path but WITHOUT the value head, frozen.
# We keep ref_model on CPU to save VRAM; only call it during KL computation
# on a small batch of action tokens.
```

Gradient checkpointing is enabled AFTER the value-head wrap with
`use_reentrant=False` — same fix as `training/train.py:763`.

### 2.3 Per-step rollout shape

For each training episode we collect a list of **transitions**:

```python
@dataclass
class Transition:
    prompt_ids: torch.Tensor       # the observation prompt as tokens (variable length)
    action_ids: torch.Tensor       # the model's action JSON as tokens
    old_logprobs: torch.Tensor     # sum(log π_old(a_t | s_t)) per action token
    value: float                   # V(s_t) at time of generation
    reward: float                  # raw env reward for THIS action
    done: bool                     # episode terminated AFTER this action
    info: dict                     # for logging: parse_ok, action_type, etc.
```

One episode is a list of (model_actions_taken) transitions — at K=1,
that's exactly the number of A0 turns survived (~5-30). At K=5, the
model still emits a plan of 5 but we treat each of those 5 as
*independent transitions* with the env reward of the actual step. (See
§3.2 — multi-action plans become a sequence of 5 separate (s, a, r)
tuples that share a prompt.)

Heuristic-controlled steps (the other 4 agents) do NOT generate
transitions — we just call `forage_heuristic_action` and step the env.
Their rewards still accrue to A0 via `cumulative_rewards[0]` but PPO
only updates on transitions where A0 acted.

### 2.4 Advantage computation

Standard GAE-λ over the trajectory:

```
δ_t = r_t + γ * V(s_{t+1}) - V(s_t)             # TD residual
A_t = Σ_{l=0..T-t-1} (γλ)^l δ_{t+l}             # GAE
R_t = A_t + V(s_t)                              # return target for value head
```

Terminal state: `V(s_{T+1}) = 0` if episode ended (`done=True`); else
bootstrap with V(s_{T+1}) from the model.

We normalise A_t to mean=0 std=1 across the rollout batch BEFORE the PPO
update. This is the GRPO trick applied per-trajectory-batch instead of
per-prompt-group, and it's standard practice in PPO.

### 2.5 PPO loss

```
ratio = exp(new_logprob - old_logprob)          # per action token
unclipped = ratio * A_t
clipped   = clamp(ratio, 1-ε, 1+ε) * A_t
policy_loss = -mean(min(unclipped, clipped))    # standard PPO objective

value_loss  = mean((V(s_t) - R_t)^2)            # MSE, no clipping
entropy     = mean(-Σ π log π)                  # over action token positions
kl          = mean(new_logprob - ref_logprob)   # KL to reference, optional

total = policy_loss + c_v * value_loss - c_e * entropy + β * kl
```

We start with `ε=0.2, c_v=0.5, c_e=0.01, β=0.04`. These are TRL's PPO
defaults plus the GRPO β we're already using.

`new_logprob` for an action: we re-tokenise `prompt + action`, run a
forward pass, and sum log-softmax(logits)[action_token_positions]. This is
the exact same computation `trl.PPOTrainer` does — we copy the helper.

## 3. File-by-file changes

We keep `training/train.py` untouched so GRPO experiments stay
reproducible. New files marked **NEW**, existing ones marked with the
change scope.

### 3.1 `training/train_ppo.py` (NEW)

Entry point. Mirrors `train.py`'s CLI surface where possible so the
docker command barely changes. New flags:

```
--rollout-episodes 8         # episodes per outer step (vs G generations in GRPO)
--ppo-epochs 4               # PPO inner update epochs
--ppo-minibatch 32           # transitions per minibatch
--clip-eps 0.2
--gamma 0.99
--gae-lambda 0.95
--value-coef 0.5
--entropy-coef 0.01
--max-action-tokens 96       # token budget per action generation
--prefix-actions 1           # same flag as GRPO; default 1
```

Removed flags vs GRPO: `--num-generations`, `--step1-weight`,
`--format-bonus`, `--rollout-limit` (becomes `--max-env-steps`).

### 3.2 `training/trajectory.py` (NEW)

`Transition` dataclass + `RolloutBuffer` class. Responsibilities:

- Collect transitions during one or more episodes.
- Implement `compute_gae(γ, λ)` that walks each episode from the end.
- Implement `iter_minibatches(batch_size, n_epochs)` that yields
  shuffled minibatches `n_epochs` times.

For K>1 plans (multi-action): the K actions share a prompt but each
action is its own transition. Old-logprobs are sliced from the same
forward pass over `prompt + action[0..K]`. Value is V(s_0) for all K
actions (a simplification — we don't re-encode for each follow-up
because the env observation hasn't actually been re-shown to the model;
the model committed to the plan up front).

### 3.3 `training/ppo_loss.py` (NEW)

Pure functions:
- `gather_action_logprobs(logits, action_ids, action_mask) → logprobs_sum_per_action`
- `ppo_clipped_loss(new_lp, old_lp, advantages, eps) → (loss, kl_est, clip_frac)`
- `value_loss(values, returns) → mse`

Each ~10 lines. Tested with a tiny synthetic minibatch in
`tests/test_ppo_loss.py` (NEW, see §3.7).

### 3.4 `training/rollout.py` (NEW)

`run_episode(model, tokenizer, env, agent_id=0, max_steps=60, prefix_actions=K)`
that returns a list of `Transition`.

Key implementation details:
- For each A0 turn, build the prompt via `build_system_prompt`, tokenise,
  call `model.generate(..., return_dict_in_generate=True,
  output_scores=True)`.
- From `output_scores` we have logits at every generated token; combined
  with the sampled token IDs we get the per-token log-probability without
  a second forward pass. Sum them → `old_logprob` for the action.
- Pull `value` from the same call: a separate `model.forward(prompt_ids)`
  with `output_hidden_states` is too slow; instead we call
  `model(prompt_ids).value` once before generate, taking the value of the
  *prompt* state s_t. (V(s_t) is a function of observation only, not
  action.) Cost: one extra small forward pass per A0 turn.
- Parse the generated text with `parse_actions(text, agent_id=0,
  max_actions=K)`. On parse failure, append a heuristic action as the
  transition's action (with `old_logprob=0` and a `parse_fail=True` info
  flag — these transitions get filtered out of the PPO update because
  their logprobs aren't comparable; they DO count in the metrics).
- For each parsed action: env.step, record reward, repeat.
- Non-A0 turns: call `forage_heuristic_action`, env.step, do NOT record
  a transition.

### 3.5 `training/inference.py` (MODIFIED)

Add `generate_with_logprobs(model, tokenizer, prompt_ids, max_new_tokens,
temperature=1.0) → (token_ids, logprobs_per_token, generated_text)`.

This is needed by §3.4. The existing `make_llm_action_fn` does not return
logprobs, so we add this as a parallel helper. The existing GRPO/eval
paths are untouched.

### 3.6 `training/metrics.py` (MODIFIED)

Add a `log_ppo_update` method alongside `log_reward_call`. Captures
per-PPO-update stats: mean policy loss, value loss, entropy, KL,
clip_frac, advantage_mean, advantage_std, ratio_min, ratio_max. The
metrics.jsonl file gains a `kind: "ppo_update"` row type alongside the
existing `kind: "reward_call"` rows. `training/plots.py` extended in a
later commit (out of scope for run 5; plain log inspection is fine).

### 3.7 `tests/test_ppo_loss.py` (NEW)

Unit tests for the math, runnable on CPU:

- `test_gather_action_logprobs_shape`
- `test_gather_action_logprobs_matches_explicit_softmax`
- `test_ppo_clipped_loss_zero_when_ratio_one`
- `test_ppo_clipped_loss_clips_above_one_plus_eps`
- `test_gae_lambda_zero_is_td_target`
- `test_gae_lambda_one_is_mc_return`

Total runtime budget: <5 seconds. These have caught more silent PPO bugs
in my experience than any number of hours of staring at TensorBoard.

### 3.8 `survivecity_v2_env/` — NO CHANGES

The env already exposes everything we need: `raw_reward` in metadata,
per-step granularity via `step()`, `current_agent_id` so we know whose
turn it is. The rubric stays. Per-step shaping rewards
(`forage_shaping`, `zombie_proximity`, `anti_camp`) become dramatically
more useful under PPO — that's exactly the signal PPO can route through
advantage estimates that GRPO drowned in a single scalar.

### 3.9 `training/eval.py` — NO CHANGES for run 5

The trained checkpoint is still a PEFT adapter loadable by `eval.py` as
today. The value head is on the SAME model object during training but
is NOT saved to the adapter (it's training-only). We save it as
`value_head.pt` in the checkpoint dir for resumability, but eval just
ignores it.

### 3.10 `Dockerfile.dgx` — NO CHANGES

`trl==0.15.2` is already pinned and contains
`AutoModelForCausalLMWithValueHead`. We are not adding deps.

## 4. Hyperparameters (initial values + justification)

| HP | Value | Why |
|---|---|---|
| `--rollout-episodes` | 8 | 8 episodes × ~10-30 transitions = 80-240 transitions/outer-step. Matches GRPO's 8 generations for fair comparison. |
| `--max-env-steps` | 60 | Same as current `--rollout-limit`. Episode usually ends earlier. |
| `--ppo-epochs` | 4 | Standard PPO default. More wastes compute, fewer underfits within the rollout window. |
| `--ppo-minibatch` | 32 | At 80-240 transitions we want 3-8 minibatches per epoch. 32 is a clean middle. |
| `--clip-eps` | 0.2 | Standard. 0.1 if we see clip_frac > 50% (signals overly large updates). |
| `--gamma` | 0.99 | Long horizon (60 steps) — γ=0.95 would discount terminal reward by 0.95^60 ≈ 5% which is too aggressive. |
| `--gae-lambda` | 0.95 | Standard. |
| `--value-coef` | 0.5 | TRL default. |
| `--entropy-coef` | 0.01 | TRL default. Watch for it killing exploration if logprobs collapse. |
| `--lr` | 1e-5 (LoRA), 1e-4 (value head) | LoRA at the GRPO value; value head can take a higher LR since it's small and from scratch. |
| `--beta` (KL to ref) | 0.02 | Half the GRPO value. PPO with explicit advantages doesn't need as much KL pressure to stay near ref. |
| `--max-action-tokens` | 96 | Same as eval. K=1 actions average ~40 tokens; K=5 plans average ~120, so we'd raise this to 192 for K=5. |
| `--max-steps` | 30 | One outer step ≈ 8 episodes × ~20 transitions ≈ 4 PPO epochs of 5 minibatches. ~3 min/outer-step on V100 (estimate, see §5). 30 outer steps ≈ 90 min — fits in a single docker session. |
| `--save-steps` | 5 | Every 5 outer-steps. 6 saved checkpoints over 30 steps. |
| `--prefix-actions` | 1 | Start with K=1 for cleanest PPO baseline. K=5 is a knob we can re-enable once K=1 works (see §7). |

## 5. Memory & throughput budget (V100 32 GB, A0-only)

| Cost | Estimate |
|---|---|
| Base model (3B, 4-bit) | ~2.5 GB |
| LoRA r=32 grads + opt state | ~0.4 GB |
| Value head (Linear 2560→1) | ~0.01 GB |
| Reference model (3B, 4-bit, no grad) | ~2.5 GB (kept on CPU, swap in for KL batch only — alt: skip ref entirely, β=0) |
| Activations (grad checkpointing on, prompt 1.5K + action 96 tokens) | ~6 GB |
| KV cache during generation | ~1 GB |
| Working overhead (HF, datasets, our buffer) | ~1 GB |
| **Peak total** | **~13-14 GB** |
| Free headroom on V100 32G | ~18 GB |

Wall clock per outer step:
- Rollout: 8 episodes × ~20 A0 turns × (1 forward V(s) + 1 generate of 96 tokens) ≈ 8 × 20 × 0.5s ≈ 80s
- Heuristic step env churn: 8 episodes × ~250 non-A0 env.step() calls ≈ trivial (~5s)
- PPO update: 4 epochs × 5 minibatches × (1 forward + 1 backward on 32 transitions of ~96 tokens) ≈ 20 × 1.5s ≈ 30s
- KL ref forward: ~10s
- **Total per outer step: ~2 min** → 30 outer steps in ~60 min on a clean GPU.

Compare to GRPO run 4: 8 generations × 4 grad_accum = 32 generations/step × ~3s/generation + ~30s update = ~2 min/step. Same order of magnitude — PPO isn't more expensive, it's just structured differently.

## 6. Risks & mitigations

### R1 — Value head doesn't learn

V(s) over a 1500-token "observation description" is a hard target. If
value_loss stays > 1.0 after 5 outer steps, advantages are noise.

**Mitigations:**
- Higher LR for the value head (already proposed: 1e-4).
- Optional value-head warmup: 1 outer step of pure value training
  (policy frozen, just value MSE) before joint PPO. Behind a flag.
- Plot V(s) vs actual return for a few held-out states. Eyeball check.

### R2 — Logprob round-trip mismatch

If `model.generate()` doesn't produce the same logprobs as a fresh
`model.forward()` on the same `(prompt+action)`, the PPO ratio is wrong
and training is silent garbage. PEFT + 4-bit + grad-checkpointing can
cause subtle numerical drift here.

**Mitigations:**
- Validation gate 2 (§1). Hard abort on first outer step if mismatch >1e-3.
- If it fails: fall back to recomputing old_logprobs via a single
  forward pass per episode immediately after rollout. Wastes ~10% of
  rollout time, but is the standard PPO recipe and avoids the drift.

### R3 — Episode reward signal is too sparse

A0 acts ~5-30 times per episode. Most of those actions get small
shaping rewards. The big signal is the terminal +0.5 / -0.5 for alive /
dead at end. Advantages on early actions may be dominated by V(s) noise
rather than reward differences.

**Mitigations:**
- Tune γ down to 0.95 if value head can't reach back 30 steps. Trade-off
  is short-sighted policy.
- Bigger entropy_coef early (anneal from 0.05 → 0.01) so the policy
  doesn't collapse to a single action while V is bad.
- Watch advantage_std in `[ppo]` log lines. If it drops below 0.1 on
  outer step >5, we're in trouble — pause and diagnose.

### R4 — Parse failures during rollout

Untrained Qwen2.5-3B emits well-formatted JSON ~95% of the time on the
single-action prompt; multi-action is ~85%. A parse failure means we
substitute a heuristic action and exclude that transition from PPO.

**Mitigations:**
- Filter parse-fail transitions out of the PPO buffer (don't compute
  ratio on actions we didn't actually sample).
- Track parse_ok rate in metrics. If it drops below 70% on any outer
  step, abort — the policy has drifted into non-JSON territory.
- Use `temperature=0.7` during rollout (vs 1.0 for GRPO) — small bias
  toward higher-prob tokens reduces malformed JSON.

### R5 — `AutoModelForCausalLMWithValueHead` + PEFT + 4-bit interaction

TRL 0.15's value-head wrapper expects an HF causal LM under the hood.
PEFT-wrapped 4-bit base is supported but the value head's forward pass
needs the LM's hidden states, which are dequantised lazily. Memory may
spike unexpectedly.

**Mitigations:**
- Validation gate 3 (§1).
- Fall-back: implement the value head manually (one
  `nn.Linear(hidden_size, 1)` registered as a child of the LoRA-wrapped
  base). ~30 lines of code; we control everything. Behind a `--manual-value-head` flag.

### R6 — Existing GRPO checkpoints don't transfer

The v2.2 LoRA from runs 1-4 should load as a warmstart, but the value
head is fresh and needs to learn from scratch.

**Mitigations:**
- 1-step value warmup as described in R1 mitigations.
- Or: skip warmstart, train PPO from base Qwen — slower but cleaner
  ablation. Default to skipping warmstart in run 5.

## 7. Phased delivery

### Phase A — Minimum-viable PPO (run 5 target)

- All of §3.1-§3.7
- A0-only, K=1, no multi-agent, no fancy curriculum
- Goal: beat heuristic on `mean_alive_at_end` over 30 eval episodes
- Time budget: 1-2 dev days + 1 DGX session (~1h for the run)

### Phase B — If A succeeds: longer training + K>1

- Re-enable `--prefix-actions 5`. Multi-action plans become 5
  transitions sharing a prompt. We already designed for this in §3.2.
- Push `--max-steps` to 100.
- Optionally enable advantage normalisation per-episode instead of
  per-batch.

### Phase C — If A fails: diagnose then escalate

- Inspect `advantage_std`, `value_loss`, `kl` trajectories.
- If value_loss is the bottleneck: pretrain value head from heuristic
  rollouts (supervised regression to actual returns). One DGX hour.
- If exploration is the bottleneck: SFT bootstrap from heuristic
  trajectories first. This is Option B from the earlier conversation
  ("Bootstrap with SFT, then RL") — keep it on the table as plan B.
- If both fail: the 3B model is the bottleneck. Switch to Qwen2.5-7B.
  Out of scope for this plan; would need separate planning doc.

## 8. Concrete next actions (in implementation order)

Each is one PR-sized commit. We do NOT batch them — one at a time, with
the unit tests passing locally before the next.

1. `training/ppo_loss.py` + `tests/test_ppo_loss.py`. Pure math; runs
   on CPU; no ML deps beyond torch.
2. `training/trajectory.py`. Dataclass + GAE + minibatch iterator.
   Tested with a hand-crafted 5-transition fake episode.
3. `training/inference.py` — add `generate_with_logprobs`. Tested by
   round-trip on a tiny Qwen-style model loaded with `device_map="cpu"`
   (or skipped on CPU-only env; tested in docker).
4. `training/rollout.py`. End-to-end rollout against
   `SurviveCityV2Env`. Sanity-check: 1 episode → list of transitions
   with non-zero logprobs and finite values. Local CPU run on a tiny
   model (`Qwen/Qwen2.5-0.5B-Instruct`) for smoke; full run on DGX.
5. `training/train_ppo.py`. The trainer loop. First DGX run:
   `--max-steps 2 --rollout-episodes 2` to verify the full pipeline
   end-to-end without burning time.
6. Real run 5: `--max-steps 30 --rollout-episodes 8 --prefix-actions 1`.
7. Eval the resulting checkpoints with the existing
   `python -m training.eval` (no eval changes needed).

After step 5 we know whether the architecture works. After step 7 we
know whether the approach beats the heuristic. Steps 1-5 are about a
day of careful coding. Steps 6-7 are one DGX session.

## 10. Decision points / open questions for the user

These don't block starting; flag them in the PR.

1. **Warmstart from run-4 LoRA, or fresh?**
